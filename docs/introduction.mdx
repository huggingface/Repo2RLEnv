Repo2RLEnv builds **RL training and evaluation tasks for coding agents**. It turns
existing code and task material into a [Harbor task](concepts/tasks.mdx): an
instruction, a starting environment, a verifier and a reference solution.

Repo2RLEnv generates and reviews the tasks. **Harbor runs agents against them.**
You can keep tasks locally or publish them on the Hugging Face Hub.

## Pick your starting point

| You have | Start here |
|---|---|
| A repository and want a first export | [Quickstart](quickstart.mdx): mine PRs with `pr_diff`, without executing target code |
| Merged PRs that need individual investigation | [Tasksmith](pipelines/tasksmith.md): author, build and review on a remote worker |
| A research method you want to reproduce | [Research recipes](pipelines/owned_recipes.md): SWE-smith, R2E, SETA and other in-repo implementations |
| Recorded agent sessions | [Trajectory to environment](pipelines/trajectory_to_env.md): repair, build, extend and question-answering tasks |
| Existing Harbor tasks | [Run with Harbor](guides/run-with-harbor.mdx) or [review their quality](concepts/quality.mdx) |

[Choose a pipeline](choose-a-pipeline.mdx) compares all routes. Native generators
use local Docker when they execute code; Tasksmith and research recipes use Modal
or Daytona workers. Supported GPU trials use Modal.

## What you get

```files
task/
├── instruction.md     # the learner's request
├── task.toml          # resources, provenance and evaluation label
├── environment/       # the starting image and build context
├── tests/             # private verifier and reward writer
└── solution/          # reference solution, also called the oracle
```

Most rewards come from deterministic tests or state checks. `pr_diff` combines
patch similarity with a required correctness judge; SCALER and FrontierSmith use
reasoning and optimization scores. [Rewards](concepts/rewards.mdx) explains the differences.

## What counts as ready

An export records what its generator checked. It is not a general quality guarantee.
Check the reference solution, the untouched baseline, the instruction and the
verifier. The [quality loop](pipelines/quality_loop.md) can add verifier probes,
blind rollouts and bounded repairs for supported tasks.

[Evaluation labels](pipelines/task_evaluation_labels.md) preserve the outcome for
the exact task revision. A task can be sound even when a solver fails it.
Published dataset counts and validation evidence live in the
[release inventory](pipelines/releases.md); measured costs live in
[yield and cost](pipelines/economics.md).
